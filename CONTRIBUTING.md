# Contributing to HyperMail

Thanks for your interest in HyperMail. This document covers everything you need to land a clean PR.

For the deeper technical briefing — environment pins, layout, conventions — read [`AGENTS.md`](AGENTS.md) first.

## Ground rules

- **Code of Conduct:** [`CODE_OF_CONDUCT.md`](CODE_OF_CONDUCT.md) (Contributor Covenant v2.1) — applies to every project space, including issues, PRs, and discussions.
- **Security issues:** do **not** open a public issue. Use [`SECURITY.md`](SECURITY.md) — GitHub's private security advisory flow.
- **License:** by contributing, you agree that your contributions are licensed under the project's [MIT License](LICENSE).

## Development setup

Prerequisites: Node 20, Git, and the native build tools `keytar` needs on your platform (`libsecret-1-dev` on Linux; Python + C++ build tools on Windows).

```bash
git clone https://github.com/danielvictorino/HyperMail.git
cd HyperMail
cp .env.example .env   # fill GOOGLE_OAUTH_CLIENT_ID + any optional AI keys
npm install
npm run dev
```

## Branching + PR flow

- `main` is protected. Direct pushes are blocked — **every change goes through a PR**.
- Branch from `main` with a descriptive name:
  - `feat/<short-name>` — new features
  - `fix/<short-name>` — bug fixes
  - `chore/<short-name>` — refactors, deps, non-feature plumbing
  - `docs/<short-name>` — documentation only
- Keep PRs small and focused. One logical change per PR.
- CI (`verify.yml`) runs on every PR across Ubuntu + Windows and must be green before merge.

## Commit messages — Conventional Commits

The repo uses [release-please](https://github.com/googleapis/release-please) to generate the `CHANGELOG.md` and cut releases. That means every commit message on `main` must follow [Conventional Commits](https://www.conventionalcommits.org):

```
<type>(<optional-scope>): <short summary>

<optional body>

<optional footer(s)>
```

Common types: `feat`, `fix`, `chore`, `docs`, `refactor`, `perf`, `test`, `ci`, `build`.

**Breaking changes** must include `!` after the type/scope *and* a `BREAKING CHANGE:` footer.

Examples:

```
feat(ai): add Anthropic fallback routing
fix(oauth): honor Retry-After on token refresh
docs(readme): fix broken link to security model
feat!: require Node 22

BREAKING CHANGE: minimum Node version bumped from 20 to 22.
```

## The verify gate

Before pushing, run the full regression gate locally:

```bash
npm run verify   # lint + format:check + typecheck + test + build
```

If that's green, CI will be green too. If you need faster iteration:

```bash
npm run test -- src/shared/ai/mail-assistant.test.ts   # single file
npm run test:watch                                     # watch mode
npm run lint:fix                                       # autofix
npm run format                                         # prettier --write
```

## Tests

- Every new feature needs tests. Bug fixes should add a regression test that fails without the fix.
- Tests live next to the code: `foo.ts` pairs with `foo.test.ts`.
- Fixtures **must** use RFC 2606-safe example addresses: `example.com`, `example.org`, `example.net`. The canonical fixture person is `Alex Example <alex@example.com>`.
- Do not commit real credentials, tokens, or personal email addresses in fixtures.

## Architecture guardrails

A few non-negotiables — these exist for safety/stability, not style:

- **IPC boundary:** new mutating IPC channels must go through `parseIpcPayload(channel, schema, input)` in `electron/main.ts`, with a zod schema declared in `src/shared/ipc-contracts.ts`. See [`docs/security.md`](docs/security.md) for the full threat model.
- **OAuth / Gmail errors:** route through the shared retry helper in `electron/runtime/retry.ts`. Don't add ad-hoc fetch loops — extend the transient classifier instead.
- **Secrets:** never commit real API keys or tokens. Use `keytar` for any new credential storage.
- **Minimize blast radius:** match the existing `docs/` tone — tight, reasoned, minimal churn. Don't refactor adjacent code unless the task requires it.

## Documentation

- User-facing changes → update `README.md` and `docs/index.md` (they need to stay in sync).
- Security posture changes → update `docs/security.md`.
- Process / smoke-test changes → update `docs/smoke-test-checklist.md` or `docs/distribution-playbook.md`.
- Don't hand-edit `CHANGELOG.md` — it's generated by `release-please` from conventional commit messages.
